# DynamoDB スケーリング戦略

## 概要

画像管理システムのDynamoDBテーブルは、**PAY_PER_REQUEST（オンデマンド）**課金モードを採用しています。このドキュメントでは、オンデマンドモードを選択した理由と、Auto Scalingが不要である理由を説明します。

## 課金モードの比較

### 1. プロビジョンドキャパシティモード
- **特徴**: 事前に読み取り/書き込みキャパシティユニット（RCU/WCU）を設定
- **Auto Scaling**: 必要（トラフィックに応じてRCU/WCUを自動調整）
- **コスト**: 予測可能なトラフィックの場合、コスト効率が良い
- **適用場面**: トラフィックパターンが予測可能で安定している場合

### 2. オンデマンドモード（採用）
- **特徴**: トラフィックに応じて自動的にスケール
- **Auto Scaling**: 不要（DynamoDBが自動的に処理）
- **コスト**: 使用した分だけ課金（リクエスト単位）
- **適用場面**: トラフィックが予測不可能、または変動が大きい場合

## オンデマンドモードを選択した理由

### 1. トラフィックの予測不可能性
- **運用開始初期段階**: ユーザー数やアクセスパターンが不明
- **画像アップロード**: バースト的なトラフィックが発生する可能性
- **公開画面アクセス**: 時間帯や曜日によって大きく変動

### 2. 管理オーバーヘッドの削減
- **キャパシティプランニング不要**: RCU/WCUの計算や調整が不要
- **Auto Scaling設定不要**: スケーリングポリシーの設定や監視が不要
- **運用負荷軽減**: インフラ管理に集中できる

### 3. 自動的なスケーリング対応
- **即座にスケール**: トラフィック増加に即座に対応
- **スロットリングなし**: キャパシティ不足によるエラーを回避
- **柔軟性**: 予期しないトラフィックスパイクにも対応

### 4. コスト効率
- **初期段階**: トラフィックが少ない場合、プロビジョンドより安価
- **無駄なコスト削減**: 未使用のキャパシティに対する課金なし
- **スケールダウン**: トラフィック減少時も自動的にコスト削減

## テーブル別の設定

### 1. 画像メタデータテーブル（ImagesTable）
```typescript
billingMode: dynamodb.BillingMode.PAY_PER_REQUEST
```

**理由**:
- 画像アップロード時のバースト的な書き込み
- 公開画面での読み取りトラフィックの変動
- GSI（GSI1、GSI2）も自動的にオンデマンドモードで動作

**アクセスパターン**:
- 画像アップロード: 書き込み集中（バースト）
- 管理画面: ページネーション読み取り（中程度）
- 公開画面: 無限スクロール読み取り（高頻度）

### 2. タグ管理テーブル（TagsTable）
```typescript
billingMode: dynamodb.BillingMode.PAY_PER_REQUEST
```

**理由**:
- タグ操作の頻度が低い
- オートコンプリート時の読み取りが不定期
- 使用回数更新の書き込みが散発的

**アクセスパターン**:
- タグ追加/削除: 低頻度
- オートコンプリート: 中頻度
- タグ一覧取得: 低頻度

### 3. ユーザー情報テーブル（UsersTable）
```typescript
billingMode: dynamodb.BillingMode.PAY_PER_REQUEST
```

**理由**:
- ユーザー操作の頻度が低い
- ログイン時の読み取りが散発的
- ユーザー情報更新が不定期

**アクセスパターン**:
- ログイン: 低〜中頻度
- ユーザー情報更新: 低頻度
- ユーザー一覧取得: 低頻度（管理者のみ）

## Auto Scalingが不要な理由

### オンデマンドモードの自動スケーリング機能

1. **自動キャパシティ管理**
   - DynamoDBが内部的にキャパシティを管理
   - トラフィック増加時に自動的にスケールアップ
   - トラフィック減少時に自動的にスケールダウン

2. **設定不要**
   - Auto Scalingポリシーの設定不要
   - ターゲット使用率の設定不要
   - スケーリングアラームの設定不要

3. **即座の対応**
   - プロビジョンドモードのAuto Scalingより高速
   - スケーリング待機時間なし
   - スロットリングリスクの最小化

## コスト最適化の考慮事項

### 将来的なプロビジョンドモードへの移行

以下の条件が満たされた場合、プロビジョンドモードへの移行を検討:

1. **トラフィックパターンの安定化**
   - 3ヶ月以上の運用データが蓄積
   - アクセスパターンが予測可能
   - ピーク時とオフピーク時の差が小さい

2. **コスト分析**
   - オンデマンドモードのコストが高い
   - プロビジョンドモード + Auto Scalingの方が安価
   - Reserved Capacityの活用が可能

3. **運用体制の確立**
   - キャパシティプランニングのノウハウ蓄積
   - 監視・アラート体制の整備
   - Auto Scalingポリシーの最適化が可能

### コスト監視

CloudWatch メトリクスで以下を監視:
- `ConsumedReadCapacityUnits`: 読み取りキャパシティ使用量
- `ConsumedWriteCapacityUnits`: 書き込みキャパシティ使用量
- `UserErrors`: スロットリングエラー（オンデマンドでは通常発生しない）

## まとめ

### 現在の設定（オンデマンドモード）

✅ **メリット**:
- Auto Scaling設定不要
- トラフィック変動に自動対応
- 管理オーバーヘッド最小
- 初期段階のコスト効率

❌ **デメリット**:
- 高トラフィック時のコストが高い可能性
- Reserved Capacityの活用不可

### 推奨事項

1. **現在**: オンデマンドモードを継続
2. **3ヶ月後**: トラフィックパターンとコストを分析
3. **必要に応じて**: プロビジョンドモード + Auto Scalingへの移行を検討
